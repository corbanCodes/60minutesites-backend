Guides

Permanent database (Postgres) — so deploys NEVER touch your data critical

Why: without a database service, the CRM writes to a file inside the app container. Railway replaces the container on every deploy, so that file — leads, notes, customers, tasks — is erased each time. Postgres lives outside the container and survives everything.

  1. Railway → your project canvas → + Create → Database → Add PostgreSQL. A "Postgres" card appears next to "web".
  2. Click the web service → Variables → New Variable: name DATABASE_URL, value ${{'{{'}}Postgres.DATABASE_URL{{'}}'}} (type it exactly — it references the Postgres card). Railway redeploys automatically.
  3. Open HQ — the app builds its tables in Postgres on first boot, and the Database row above turns green. From then on, deploy as often as you like.
  4. If you have a backup file, restore it below (Backups) to load your data in.

Bonus: Railway Postgres supports its own backups (Postgres card → Backups tab) — turn on daily backups there for belt-and-suspenders.

Backups — export & restore the whole CRM 30 seconds, do it often

Downloads everything — customers (with logins), leads, notes, tasks, forms, and sites (including their HTML) — as one JSON file. Restore inserts anything missing and never overwrites existing rows, so it's always safe to run. (Uploaded images/flipbook PDFs aren't included — those live in the DB media table and are re-uploadable.)

GitHub publishing — the ONE token that makes client edits go live do this once, never again

How publishing works: each client site links to a GitHub repo. When anyone hits Save in the editor, HQ commits the page to that repo, and Netlify (watching the repo) redeploys the client's real domain within a minute. The missing piece is a single server-side token — set once for ALL sites and all future clients. You do NOT need a new token per site or per save.

  1. Go to github.com/settings/personal-access-tokens → Generate new token (fine-grained).
  2. Name it 60ms-hq-publisher. Expiration: 1 year (put a task in Tasks to renew it — seriously, do it now).
  3. Repository access: “Only select repositories” → tick every client repo (e.g. corbanCodes/toddtrope). You'll add new client repos to this same token later.
  4. Permissions → Repository permissions → Contents: Read and write. Nothing else.
  5. Generate, copy the github_pat_… value.
  6. Railway → your app service → Variables → add GITHUB_TOKEN = the token → it redeploys automatically.
  7. Come back here → Test connection. It checks the token AND every linked repo, and tells you exactly which repo is missing access if any.

When you onboard a new client later, the only GitHub chore is: add their repo to this token's repository list (github.com/settings/personal-access-tokens → your token → Repository access).

Link an EXISTING site to its repo the Todd situation

Already created the site in HQ (uploaded/built it) but it's not connected to GitHub? You don't need to recreate anything:

  1. If the repo doesn't exist yet: github.com/new → name it after the client (e.g. toddtrope) → create it empty (no README needed).
  2. If GitHub publishing is on (guide above), make sure this repo is in the token's repository list.
  3. Sites → find the site → “Link repo” → type owner/repo → keep “push current version now” checked → Link. HQ verifies access and pushes the current page as the first commit.
  4. Netlify → Add new site → Import an existing project → GitHub → pick the repo → deploy. Then Domain settings → add the client's custom domain and follow the DNS records it shows.
  5. Prove the loop: open the editor, change one word, Save — the Sites page will show live with a timestamp, and the commit appears in GitHub.

“Push now” on the Sites page re-publishes any time without opening the editor. If a push fails you'll see exactly why, right on the row (and as an alert up top).

Onboard a paying client, start to finish
  1. Customers → Add — name, email, cell, monthly price + setup fee (you can fill these in later too — there's a reminder if you skip it). Copy the generated password; text it to them.
  2. Site: either Sites → + New site (template or GitHub import, Owner = the client), or link an existing site's repo (guide above).
  3. Forms → Create — name it after them, Owner = the client. In the editor, “+ Form” and pick their form. Their submissions land in their CRM (you still see everything as admin) and email them via Resend.
  4. Test the publish loop — editor → change a word → Save → “live” status on Sites.
  5. Log in as them once (their email + password) to see their view: their dashboard, site, CRM, tasks — nothing of yours.
  6. Money shows up automatically on Revenue once the monthly price is set.
Lead email alerts (Resend)
  1. resend.com → API Keys → create key → Railway Variables → RESEND_API_KEY.
  2. Set ADMIN_EMAIL = your email, so leads from your own forms reach you (client forms email the client automatically).
  3. Until you verify your domain at resend.com/domains, emails send from the shared test address and may only deliver to your own inbox. Verify the domain, then set RESEND_FROM = 60 Minute Sites <leads@yourdomain>.
Billing & the Revenue dashboard

Set each customer's monthly price (and one-time setup fee) on the Customers page — inline, any time, before or after creating them. Revenue then shows MRR, ARR run-rate, and a 12-month projection. Put a $/mo deal value on CRM leads and the weighted pipeline (New 10% → Built 75%) forecasts what's coming.

Editor AI (optional)

Railway Variables → OPENAI_API_KEY (platform.openai.com → API keys). Enables “AI rewrite” on any text and “AI restyle” for whole-page design instructions in the site editor.

Demo account — a full CRM to showcase on sales calls John Melody

Builds (or wipes and rebuilds) a fake customer — John Melody, Melody Home Services (johnmelody@gmail.com) — loaded with ~750 leads across every pipeline stage with deal values, notes, open and completed tasks, two forms, and a polished site in the editor. Log in as him in front of a prospect and let the product sell itself.

  2. Hit the button. Rebuild any time to reset the demo to a clean, full state before a pitch.
If something breaks
  • Client wrecked their page: Sites → Undo save restores the previous version and re-pushes to GitHub. Every save keeps the last 20 versions.
  • Save says the push failed: the exact reason is on the Sites row and up top here. 9 times out of 10 the repo isn't in the token's repository list.
  • Form redirect typo / wrong URL: forms can't be edited yet — delete and recreate (the embed code changes; re-paste it).
  • Railway deploy loses data: it shouldn't (Postgres) — if it ever does, check the app service still has DATABASE_URL = ${{'{{'}}Postgres.DATABASE_URL{{'}}'}}.
  • Times look off: HQ displays {{ 'America/Los_Angeles' }} by default — set APP_TZ in Railway (e.g. America/Denver) to change it.
